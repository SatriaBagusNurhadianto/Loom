## Native integration research

The requested T3 Code settings image is inspiration for provider selection and progressive runtime details. The architectural lesson from T3's [provider internals](https://github.com/pingdotgg/t3code/blob/main/docs/internals/providers.md) and [adding a provider](https://github.com/pingdotgg/t3code/blob/main/docs/internals/adding-a-provider.md) is to preserve a native harness behind an application adapter, with shared projected sessions/events/capabilities. Loom uses separate adapters and a common typed contract, rather than copying T3's complete settings or adding an internal model/tool loop. Additional harnesses require their own validated adapters; arbitrary command compatibility is not advertised.

OpenCode's [server](https://opencode.ai/docs/server/), [SDK](https://opencode.ai/docs/sdk/), [permissions](https://opencode.ai/docs/permissions/) and [MCP documentation](https://opencode.ai/docs/mcp-servers/) were consulted. The installed **2.2.1** server exposes a native `/api/...` schema that differs from the currently published SDK declarations. Implementation was checked against its actual local `/openapi.json`, actual request behavior and the pinned generated SDK's raw transport. In particular, native model selection uses POST, active sessions use a keyed data map, session terminal metadata includes idle/outcome, and actual permission/forms endpoints are handled explicitly. The SDK dependency is pinned at **1.19.5**, bundled in the utility build, and the supported server version is deliberately bounded.

Codex uses its official [app-server protocol](https://developers.openai.com/codex/app-server/) through supervised stdio, with native initialization, model/account discovery, thread start/resume, turn start/interrupt, public events, native approval requests and questions. The exercised CLI is **0.159.3**, with a **0.159.x** compatibility guard. Authentication remains owned by the installed harness; no account credentials are copied into project source, logs or fixtures.

Loom's MCP endpoint exposes three narrow local scientific-writing tools: paper structure, PDF status and PDF build scheduling. It calls the existing project/build services. This does not introduce literature search, Zotero, image generation, Git operations, generic shell tools or a custom tool-execution loop; those remain owned by their relevant phase or native harness.

See [the test guide](phase-4-testing.md) for live prerequisites and simulation boundaries. Generated artifacts are ignored local evidence. All test manuscripts are synthetic. Linux is the validated target; universal harness support, cross-platform distribution and broad researcher studies are not claimed.

The final broad local-PDF regression initially inherited an untracked automatic-build preference from the developer sample. The manual folder-recovery fixture now removes that preference only from its temporary copy; the original sample and user settings remain untouched. The focused recovery case and full nine-case live PDF regression passed after isolation. This is a test-fixture correction, not an application behavior change.

## Native execution correction and UI review

The user's actual desktop runs OpenCode 1.19.0 as well as an available 2.2.1 binary. Its own live `/openapi.json` and isolated no-inference startup probes established the separate classic native routes and runtime MCP registration. Native execution uses OpenCode's build agent and native tools; Codex uses app-server native tools in the manuscript directory. The earlier live test did not require MCP access, leaving unsupported Codex elicitation/grant handling unexercised. Protocol regressions and actual MCP-required question/edit workflows now cover that boundary.

The [Codex app-server documentation](https://learn.chatgpt.com/docs/app-server) and the installed 0.159.3 generated JSON schemas supply the native effort, sandbox, approval, MCP consent and permission-grant shapes. The [T3 Codex adapter](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts) provides the reference for supervised, auto-accept edits, auto review and full-access policy mapping. The UI never invents reasoning levels or a provider API execution loop. OpenCode has no distinct Codex auto reviewer, so its menu omits the duplicate Auto choice.

Terra review caught a failed-resume permission escalation and all-provider detection failure after a custom binary disappears. Root corrected both with service/runtime tests and extended strict session IPC validation. Subsequent review caught the inability to submit a replacement or blank/PATH runtime choice after a missing binary; the Runtime tab now permits an explicit reconnect probe, with an Electron regression. Native uncertain external cancellation stays protected rather than manufacturing confirmation.

Luna xhigh UI/UX review inspected the current provider/settings source and running-Electron screenshots against DESIGN/Prism. It found duplicate OpenCode Auto policy, misleading paper-only edit wording, numeric answer coercion and inconsistent boolean validation/focus. Those are corrected; actual Electron form/settings tests cover the results. Single-line model-search Up/Down intentionally moves to options, with Home/End retained for text editing and a keyboard selection regression. The final permission screenshot was regenerated after source changes. Reviewers did not independently execute Electron or conduct researcher interviews; root ran the desktop checks and visually inspected the generated artifacts.
