## Native integration research

The requested T3 Code settings image is inspiration for provider selection and progressive runtime details. The architectural lesson from T3's [provider internals](https://github.com/pingdotgg/t3code/blob/main/docs/internals/providers.md) and [adding a provider](https://github.com/pingdotgg/t3code/blob/main/docs/internals/adding-a-provider.md) is to preserve a native harness behind an application adapter, with shared projected sessions/events/capabilities. Loom uses separate adapters and a common typed contract, rather than copying T3's complete settings or adding an internal model/tool loop. Additional harnesses require their own validated adapters; arbitrary command compatibility is not advertised.

OpenCode's [server](https://opencode.ai/docs/server/), [SDK](https://opencode.ai/docs/sdk/), [permissions](https://opencode.ai/docs/permissions/) and [MCP documentation](https://opencode.ai/docs/mcp-servers/) were consulted. The installed **2.2.1** server exposes a native `/api/...` schema that differs from the currently published SDK declarations. Implementation was checked against its actual local `/openapi.json`, actual request behavior and the pinned generated SDK's raw transport. In particular, native model selection uses POST, active sessions use a keyed data map, session terminal metadata includes idle/outcome, and actual permission/forms endpoints are handled explicitly. The SDK dependency is pinned at **1.19.5**, bundled in the utility build, and the supported server version is deliberately bounded.

Codex uses its official [app-server protocol](https://developers.openai.com/codex/app-server/) through supervised stdio, with native initialization, model/account discovery, thread start/resume, turn start/interrupt, public events, native approval requests and questions. The exercised CLI is **0.159.3**, with a **0.159.x** compatibility guard. Authentication remains owned by the installed harness; no account credentials are copied into project source, logs or fixtures.

Loom's MCP endpoint exposes three narrow local scientific-writing tools: paper structure, PDF status and PDF build scheduling. It calls the existing project/build services. This does not introduce literature search, Zotero, image generation, Git operations, generic shell tools or a custom tool-execution loop; those remain owned by their relevant phase or native harness.

See [the test guide](phase-4-testing.md) for live prerequisites and simulation boundaries. Generated artifacts are ignored local evidence. All test manuscripts are synthetic. Linux is the validated target; universal harness support, cross-platform distribution and broad researcher studies are not claimed.
